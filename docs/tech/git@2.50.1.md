# git@2.50.1

The installed git (`git --version` → git version 2.50.1 (Apple Git-155), `/usr/bin/git` resolving to `/Applications/Xcode.app/Contents/Developer/usr/bin/git`). Official docs are versioned per release; git-scm.com/docs/<page>/2.50.1 redirects to the 2.50.0 page, the man pages shipped with the installed binary were read as well (`/Applications/Xcode.app/Contents/Developer/usr/share/man/man1/`). Experiments ran on 2026-10-24 in temporary folders, with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null` unless a line says otherwise; `{S}` = a scratch folder under `/private/tmp/.../scratchpad/t02/`. Exit codes are those of the command named. No window was opened and no real repository was touched. For the plan: `projects/git.ts` (D14), the project map (D5, D11), `git init` of a new project (D4).

## git init

- `git init <dir>` creates `<dir>/.git` and prints "Initialized empty Git repository in <dir>/.git/", exit 0; the initial branch of the installed git is `main` (`git symbolic-ref HEAD` → `refs/heads/main`). The name does not come from git's built-in default (`master`): Apple's own file `/Applications/Xcode.app/Contents/Developer/usr/share/git-core/gitconfig` sets `init.defaultBranch=main` (`git config --show-origin --get-all init.defaultBranch` → `file:/Applications/.../git-core/gitconfig main`), and `GIT_CONFIG_SYSTEM=/dev/null`, an empty `HOME` and `env -i` all still gave `main`. A user's global `init.defaultBranch` overrides it; `git init --initial-branch=<name>` overrides both — https://git-scm.com/docs/git-init/2.50.0 and https://git-scm.com/docs/git-config/2.50.0 ("Allows overriding the default branch name e.g. when initializing a new repository.")
- `.git/hooks/` is created with 14 `*.sample` files copied from the template directory, none of them active (a hook runs only without the `.sample` suffix); `git init --template= <dir>` creates an empty `hooks/` (`ls | wc -l` → 1 line, the `total` line of an empty listing) — https://git-scm.com/docs/git-init/2.50.0 (`--template`)
- `git init` into an existing non-empty folder: exit 0, existing files untouched (`{S}/b` with one file `f` → `.git f`). Into a folder that already is a repository: "Reinitialized existing Git repository in <dir>/.git/", exit 0, nothing destroyed — so `init` cannot tell the app that the folder was already a repository; the app checks with `rev-parse` first if it needs to know. `mkdir` failure: `git init /nonexistent_zz/q` → "fatal: cannot mkdir /nonexistent_zz/q: Read-only file system", exit 128; `git init <path to a regular file>` → "fatal: cannot mkdir file: File exists", exit 128 — https://git-scm.com/docs/git-init/2.50.0
- `git init` in a repository owned by another user (see safe.directory below): "Reinitialized", exit 0, no refusal.

## ls-files and rev-parse

- `git ls-files --cached --others --exclude-standard` lists tracked plus untracked-and-not-ignored files, relative to the current directory, one per line, no directories; a path listed in `.gitignore` is absent (`{S}/nc`: files `.gitignore a b`, ignored `ign` missing), exit 0 — https://git-scm.com/docs/git-ls-files/2.50.0
- A repository without commits: the same output (index plus untracked), exit 0; the index is empty, so every file is "other" (`{S}/nc`).
- Not a repository (and no parent is one): "fatal: not a git repository (or any of the parent directories): .git", exit 128, for `ls-files` and for `rev-parse --show-toplevel` alike. A non-repository folder inside a temp folder that is itself inside a repository would resolve to that outer repository, so the exit code alone does not prove "not a repository"; compare `rev-parse --show-toplevel` with the folder's realpath (next lines).
- Inside a subfolder of a larger repository, `git ls-files --cached --others --exclude-standard -- .` lists only that subtree, paths relative to the subfolder (`sub/` with `s1`, `deep/s2`, untracked `untracked` → `untracked`, `deep/s2`, `s1`, exit 0); without `-- .` the output is the same because git limits `ls-files` to the current directory by default, but D11 keeps the explicit `-- .`. `git rev-parse --show-toplevel` from that subfolder prints the outer repository root (`{S}/big`), not the subfolder, so "project folder == toplevel" is a test the app can make: when they differ, the project is inside a larger repository (D11).
- Submodules: `ls-files --cached --others --exclude-standard` lists the submodule as one entry (`libsub`) plus `.gitmodules`; files inside it, tracked or untracked, are not listed (`{S}/sm`: `libsub/new` absent), exit 0. `--recurse-submodules` combined with `--others` is refused: "fatal: ls-files --recurse-submodules unsupported mode" (exit 128, run again without a pipe). The map therefore shows a submodule as a single path — https://git-scm.com/docs/git-ls-files/2.50.0
- Symlinks: a symlink is listed as a plain path whether it points at a file or at a directory (`link` → `../outside.txt`, `dirlink` → `../outdir` both listed, exit 0, mode `120000` after `git add`), and `ls-files` never follows it or lists what is behind a directory symlink (`outdir/z` absent). Listing therefore never reaches outside the project, but a later read of a listed path does follow the link: the map reads only after realpath of the file stays inside the realpath of the project (D5). Targets: a symlink pointing outside is listed, so the read-side check is the only defence.
- Realpath of the project: `git -C <symlink-to-repo> rev-parse --show-toplevel` prints the resolved path (`{S}/sl`, while `pwd` inside the link says `{S}/slroot` and `pwd -P` says `{S}/sl`); `ls-files` output is relative, so it carries no prefix to compare. On macOS `/tmp` and `/var` are symlinks to `/private/...`: compare with `fs.realpath` of the project, never with the string the picker returned — https://git-scm.com/docs/git-rev-parse/2.50.0 (`--show-toplevel`: "Show the (by default, absolute) path of the top-level directory of the working tree")

## /usr/bin/git without Command Line Tools

- Here: `xcode-select -p` → `/Applications/Xcode.app/Contents/Developer`, exit 0; `pkgutil --pkg-info=com.apple.pkg.CLTools_Executables` exists; `xcrun --find git` → `/Applications/Xcode.app/Contents/Developer/usr/bin/git`. `/usr/bin/git` is a 200 KB shim (`ls -l` → 200560 bytes) that runs the git of the active developer directory; `DEVELOPER_DIR=/nonexistent /usr/bin/git --version` → "xcrun: error: missing DEVELOPER_DIR path: /nonexistent", exit 1. The no-tools state itself was not reproduced: it would open the install dialog on the owner's screen.
- Evidence from public sources (not Apple documentation, read through a web search on 2026-10-24): on a Mac without Command Line Tools `/usr/bin/git` is a stub; `git --version` prints "xcode-select: note: No developer tools were found, requesting install." and exits 1 (the text says it opens the install dialog), and `xcode-select -p` fails with "error: unable to get active developer directory" — https://github.com/Jason-Vaughan/TangleClaw/issues/788 , https://mac.install.guide/commandlinetools/9 , https://deverrors.com/errors/git-macos-xcode-select-install . A headless session shows another error ("no install could be requested, perhaps no UI is present") — https://developer.apple.com/forums/thread/21448 . These pages were found by search snippets; the exact exit code of `xcode-select -p` in that state (documented only as "error") was not read from a primary source: no Apple page was found that states it. Apple's own page on the tools is https://developer.apple.com/library/archive/technotes/tn2339/_index.html (not read for this note).
- Verdict: community evidence exists and is consistent (stub prints the note, exits non-zero, opens a dialog; `xcode-select -p` errors without tools), so the D14 gate is supported by third-party evidence only; no Apple page states the exit code of `xcode-select -p` without tools. Runner rule that needs no exit code: run `xcode-select -p` first on darwin and treat any non-zero exit or a missing path on disk (`fs.existsSync(<path>/usr/bin/git)` false) as "git unavailable", and never call `/usr/bin/git` in that case, so the dialog never opens.

## safe.directory

- Git "will refuse to even parse a Git config of a repository owned by someone else, let alone run its hooks"; `safe.directory` "is only respected in protected configuration" (system, global, command-line `-c`, not the repository's own `.git/config`) — https://git-scm.com/docs/git-config/2.50.0 (`safe.directory`)
- Reproduced with `GIT_TEST_ASSUME_DIFFERENT_OWNER=1` (git's own switch for its tests; a real foreign-owned folder needs root to create): `git ls-files --cached --others --exclude-standard` and `git rev-parse --show-toplevel` → "fatal: detected dubious ownership in repository at '<dir>'" plus the "To add an exception ... git config --global --add safe.directory <dir>" hint, exit 128 for both. `git -c safe.directory=<dir> ls-files --others` works (exit 0), as does a global `safe.directory = *`. The runner must not pass such `-c` itself: the owner decides, so exit 128 with "dubious ownership" in stderr is shown as a readable error and the map falls back to the directory walk (D14).
- Consequence for the hostile-config tests below: a repository owned by another user is never parsed, so the hostile keys matter only for folders owned by the same user (a zip or tarball of a repository with its `.git`, a folder synced from elsewhere); `git clone` does not copy the source's `.git/config`.

## Which config keys of a hostile .git/config run

Setup: a repository `{S}/hs` with a commit, a modified tracked file and an untracked file, `.git/config` with `core.fsmonitor`, `core.hooksPath` (pointing at a folder with executable `post-checkout`, `post-commit`, `post-merge`, `reference-transaction`, `pre-commit`), `core.pager`, `core.sshCommand`, `core.editor`, `core.askPass`, `core.gitProxy`, `diff.external`, `credential.helper` and an `alias.ls`, each a script that appends a line to a marker file. Commands ran with stdout and stdin not a terminal (as from `execFile`). "fires" = marker line written.

| key | `init .` (existing repo) | `ls-files --cached --others --exclude-standard -- .` | `rev-parse --show-toplevel` | `status` / `status --porcelain` | `diff` |
|---|---|---|---|---|---|
| `core.fsmonitor` (script path) | no | **fires** (`2 <timestamp>`, the hook protocol version 2) | no | **fires** | **fires** |
| `core.hooksPath` | no | no | no | no | no (hooks fired only on `commit`: `pre-commit`, `post-commit`, `reference-transaction`) |
| `core.pager` | no | no | no | no (no terminal: no pager started) | no (same reason) |
| `core.sshCommand`, `core.gitProxy`, `core.askPass`, `credential.helper` | no | no | no | no | no |
| `core.editor` | no | no | no | no | no |
| `diff.external` | no | no | no | no | **fires** (`diffexternal a ...`) |
| `alias.*` | no | no | no | no | no |

- Result for the runner's commands (`init`, `ls-files`, `rev-parse`): only `core.fsmonitor` fires, and only for `ls-files` (the index is refreshed against the monitor) — so `-c core.fsmonitor=false` is the key override; `core.hooksPath` fires for no command the runner uses (`init`, `ls-files`, `rev-parse` run no hook; hooks run only on `commit`, `checkout`, `merge` and similar), so the override is defence in depth against a later command, not against a measured one. `status` and `diff` are not used by the runner; had they been, `core.fsmonitor` and `diff.external` would fire (`diff.external` does not fire for `ls-files`; `--no-ext-diff` would be its switch).
- Neutralised: with `-c core.hooksPath=<empty dir> -c core.fsmonitor=false` the marker stayed empty for `init .`, `ls-files`, `rev-parse` and `status` (exit 0 each); `diff` still fired `diff.external` (not covered by the two overrides, not a runner command). `core.pager` was not run on a terminal: its documented trigger is a terminal stdout — https://git-scm.com/docs/git-config/2.50.0 (`core.pager`, `core.fsmonitor`, `core.hooksPath`) and https://git-scm.com/docs/githooks/2.50.0
- `core.fsmonitor` doc (man page of the installed git): "If set to true, enable the built-in file system monitor daemon for this working directory" — a path value is the older hook form and is what ran here; `core.fsmonitor=false` turns both off. `core.hooksPath`: "By default Git will look for your hooks in the $GIT_DIR/hooks directory. Set this to different path ... and Git will try to find your hooks in that directory".
- The empty hooks directory must exist and be a directory the runner owns (a missing path also finds no hook, but an existing empty one removes the question).

## Environment

- `GIT_TERMINAL_PROMPT=0`: "If this Boolean environment variable is set to false, git will not prompt on the terminal (e.g., when asking for HTTP authentication)" — https://git-scm.com/docs/git/2.50.0 . Run: `GIT_TERMINAL_PROMPT=0 git ls-remote <https url of a missing GitHub repository>` with stdin `/dev/null` → "fatal: could not read Username for 'https://github.com': terminal prompts disabled", exit 128 in 0.6 s. The runner's commands are local (`init`, `ls-files`, `rev-parse`) and do not reach the network, so the variable is a guard for a future command, not a measured need.
- `GIT_OPTIONAL_LOCKS=0`: "Git will complete any requested operation without performing any optional sub-operations that require taking a lock. For example, this will prevent git status from refreshing the index as a side effect" — https://git-scm.com/docs/git/2.50.0 . Run (`{S}/ol`, `.git/index` mtime forced to 2020-01-01 and the tracked file touched so the index is stat-dirty): `GIT_OPTIONAL_LOCKS=0 git status` → mtime unchanged (1577822400); plain `git status` → mtime moved to now (1792796722) and the inode changed (a new index was written). `git ls-files --cached --others --exclude-standard` left the mtime unchanged even without the variable (1577822400), so for the runner's commands the variable changes nothing; it matters only if `status` is ever run against the owner's open repository.

## Findings that change the plan

- D14's "`-c core.hooksPath=<empty dir>`" is kept but measured as inert for `init`, `ls-files` and `rev-parse`; `-c core.fsmonitor=false` is the override that does work: a hostile `core.fsmonitor` script ran on `ls-files`. T16's hostile-config test is red-able with `core.fsmonitor` removed from the overrides, and can add a `core.hooksPath` marker as a guard that never fires.
- The initial branch `main` comes from Apple's `git-core/gitconfig`, not from git: do not assert the branch name in a test; read `symbolic-ref HEAD` if the name matters, or pass `--initial-branch=main`.
- `init` into an existing repository exits 0 ("Reinitialized"); the app tells the cases apart with `rev-parse --show-toplevel` before `init`.
- No `git`-level protection against a symlink listed by `ls-files`: the realpath containment check on read (D5) is the only one.
- Outside any repository, `ls-files` and `rev-parse` exit 128; a temp folder under an outer repository would resolve to it, so compare `rev-parse --show-toplevel` with the project's realpath (D11).
- Command Line Tools gate: community evidence only (no Apple page for the exit code); the gate stays, built on `xcode-select -p` exit code plus a check that its path holds `usr/bin/git`.
