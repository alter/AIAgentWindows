# claude-code@2.1.306

The installed CLI (`claude --version` → 2.1.306). Its docs are not versioned; quotes were read on 2026-10-21. `{R}` = `tasks/10-app-shell/02-room/spikes`. Room study (T01 of `tasks/10-app-shell/02-room/PLAN.md`): no prompt was sent to the CLI; the transcript facts are record shapes and counts from the owner's existing transcripts.

- `--session-id <uuid>` starts a session with that id, `--resume <id>` resumes it, `--add-dir` grants read and edit access to an extra directory; reads there need no prompt — https://code.claude.com/docs/en/cli-reference and https://code.claude.com/docs/en/permissions
- Transcripts live at `projects/<project>/<session>.jsonl` under `~/.claude` or `CLAUDE_CONFIG_DIR`; the docs call it "Full conversation transcript" and list no fields — https://code.claude.com/docs/en/claude-directory
- The project directory name comes from the resolved path: a session started in `/tmp/x` is stored under `-private-tmp-x`, so the app finds a transcript by globbing `projects/*/<id>.jsonl` (`tasks/05-feasibility/01-evidence-table/spikes/transcripts-last-reply.txt`) — https://code.claude.com/docs/en/claude-directory
- Subagent turns are written to `<session>/subagents/agent-*.jsonl`, not into the session file; the main file had no `isSidechain: true` records in a session with three subagents (`{S}/claude-subagent-files.txt`) — https://code.claude.com/docs/en/claude-directory
- One reply spans several `type: assistant` records (a `thinking` block, then `text`); the last reply is the text blocks after the last user prompt (`last_reply.py` in the spike directory) — https://code.claude.com/docs/en/claude-directory
- `Ctrl+V` (Alt+V on Windows) makes the CLI read the OS clipboard itself: an image becomes an `[Image #N]` chip, text is pasted as text (both seen in the spike screens) — https://code.claude.com/docs/en/interactive-mode
- The Linux clipboard helper Claude Code needs (xclip or wl-paste) is not named in the official docs — https://code.claude.com/docs/en/troubleshooting
- A new directory shows a workspace-trust dialog whose default choice is "No, exit" (Enter alone quits, `{S}/claude-trust-enter/run.out`); the answer is saved in the user's config — https://code.claude.com/docs/en/permissions
- Voice dictation: `/voice`, hold Space; needs a Claude.ai sign-in and a local microphone; on Linux it falls back to `arecord` or SoX `rec` when its native module cannot load — https://code.claude.com/docs/en/voice-dictation
- A `claude` that inherits `CLAUDE_CODE_CHILD_SESSION` from a Claude Code session turns transcript saving off ("Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker", `{S}/claude-resume-inherited-env.txt`); the app drops the variable when it spawns a window — https://code.claude.com/docs/en/claude-directory
- `--dangerously-skip-permissions` equals `--permission-mode bypassPermissions` — https://code.claude.com/docs/en/permission-modes
- Running the unmodified binary with the user's own subscription inside another product is allowed; the binary must not be modified and usage may not be resold or intermediated — https://code.claude.com/docs/en/legal-and-compliance
- `--permission-mode plan`: Claude "reads files, runs shell commands to explore, and writes a plan, but does not edit your source"; edits stay blocked until a plan is approved. Shell commands in plan mode go to the auto-mode classifier by default (`useAutoModeDuringPlan` on) or prompt: an approved command runs, so plan mode alone is not a guarantee that a shell command writes nothing — https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode
- Plan mode does not block anything in an interactive terminal session where `bypassPermissions` is in the mode cycle ("Claude is still instructed to plan without editing, but a file edit or shell command it attempts during planning runs without prompting"). It gets into the cycle through `--permission-mode bypassPermissions`, `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions` or `permissions.defaultMode: "bypassPermissions"` in user, `--settings` or managed settings. The owner's `~/.claude/settings.json` has `defaultMode: auto` and no managed file exists (`{R}/claude-settings-keys.txt`), so on this machine plan mode is enforced; a room session must never be started with one of those flags — https://code.claude.com/docs/en/permission-modes#skip-all-checks-with-bypasspermissions-mode and https://code.claude.com/docs/en/permission-modes#switch-permission-modes
- `ExitPlanMode` "presents a plan for approval and exits plan mode" and requires permission; a plan-mode session that decides to present a plan stops at an approval dialog and the turn does not end until a person answers. The Room's turn timeout covers it, but the dialog stays open in the pty — https://code.claude.com/docs/en/tools-reference
- `--disallowedTools` with a bare tool name removes the tool from Claude's context (`"Edit"`; `"*"` removes all); `--tools` restricts the built-in set; on macOS the default set has no `Glob`/`Grep` (Claude searches through Bash). A room claude session can therefore remove `Bash Edit Write NotebookEdit ExitPlanMode` and keep `Read` — https://code.claude.com/docs/en/cli-reference
- `--restricted` exists in 2.1.306 (`{R}/claude-help-flags.txt`): removes command-running tools and WebFetch, ignores user/project/local settings (hooks and rules of the owner do not apply), confines file tools to the working directories including `--add-dir`, refuses `bypassPermissions`. Not used by the Room until someone has started it once to see that sign-in still works; that start was not possible in this study — https://code.claude.com/docs/en/cli-reference
- End of a turn in the transcript: an assistant message is written as one record per content block (`thinking`, `text`, `tool_use`), and the message's `stop_reason` is stamped on every record of it. A final answer is `end_turn`; a message that continues into a tool is `tool_use` (`{R}/claude-turn-signal.txt`, 61 messages shaped `end_turn(thinking)` then `end_turn(text)`, 245 `end_turn(text)` alone). The first `end_turn` record is therefore not always the reply: when it holds only `thinking`, the `text` record follows. The reply is the `text` blocks of the `end_turn` records that share one `message.id`; the turn is over at the first `end_turn` record after the send time that has a `text` block (the `thinking`-only one is skipped). Records carry an ISO `timestamp`; user records carry `promptId`, `permissionMode`, `turnPosition` — https://code.claude.com/docs/en/claude-directory (the docs list no transcript fields; the shapes are from the run)
- After a final answer Claude Code writes `system` records: `stop_hook_summary` (307, `preventedContinuation` false in all of them) and `subtype: turn_duration` (keys `durationMs`, `messageCount`, `pendingBackgroundAgentCount`). A `turn_duration` record followed 288 of 307 `end_turn` records that carry text, so it confirms the end when present but is not a reliable signal alone; the driver takes `end_turn` + `text` as the end and waits a short settle time for a following `tool_use` record before it reads the reply (`{R}/claude-turn-signal.txt`; the settle time is an assumption, tested on stubs by T03) — https://code.claude.com/docs/en/claude-directory (the docs list no transcript fields; the shapes are from the run)
