# Projects and project rooms in PLAN mode

## Goal
The app is organised by projects. A project is a code directory (existing, or new: folder plus `git init`). Its agents work in that directory; its rooms discuss the project in PLAN mode: CLI participants run in the project folder in their read-only modes with the owner's and the project's hooks kept out, web and OpenRouter participants get the history plus a project map built from `git ls-files`, and the final answer is saved by a button to `<project>/docs/plans/<room slug>.md`. Agents and rooms without a project stay under a "No project" node; site logins and the OpenRouter key survive the upgrade, and a build from `main` keeps working on the same data folder. On the way the code gains the seams the next layers need — kind descriptors, one model spec, one file store, IPC by domain, a turn profile and a context pack — each cut by a behaviour-neutral task right before its second consumer. The third layer — roles and an orchestrator — is its own plan, `docs/plans/roles.md`, started after the owner's real run of a project room (AC5). Owner, 2026-10-24; reviewed and rewritten with the owner seven times the same day (Log).

The other old partitions stay on disk untouched (§5).
- D4 A new project creates the folder and runs `git init` (owner).
- D5 Web and OpenRouter participants of a project room get the room history plus an automatic project map: the file tree from `git ls-files` (no `git` or no commits: a directory walk under the same rules) and README / CLAUDE.md / AGENTS.md, with a size cap, a deny list by name (`.env*`, `*.pem`, `id_*`, `*credentials*`, `*secret*`, `settings.local.json`, `.npmrc`, `.netrc`), and paths checked against the realpath of the project (owner).
- D6 "Save plan" writes the final answer to `<project>/docs/plans/<room slug>.md`: slug sanitised (no `/`, `..`, control characters, ≤ 80 chars), no front matter added, an existing file overwritten only after confirmation, `docs/plans` refused when it resolves outside the project; models get no write access in rooms (owner).
- D7 Layers in order projects → PLAN rooms → roles (owner). Roles are `docs/plans/roles.md`, started after AC5.
- D8 CLI participants of a project room run in the project folder with their read-only flags of today plus the hook isolation found by T03, so neither the owner's `~/.claude/settings.json` hooks nor the project's own hooks drive a room turn (evidence: `~/.claude/hooks/stop-guard.sh:17-21` re-prompts any session whose cwd has a `docs/plans/*.md` with `status: running`; `session-start.sh:13` scans the same). Hooks are switched off; the project's `CLAUDE.md` / `AGENTS.md` stay loaded, they are the project context the room moved there for. The isolation is a CLI mechanism (first candidate `--settings '{"disableAllHooks":true}'`, then `--setting-sources`), never the owner's private `CC_DISABLED_HOOKS`. The room intro tells CLI participants they discuss and do not execute the project's plans. A participant's session title names the room.
- D9 Deleting a project never touches its code folder: it leaves the index, every service closes its part (D20: pty agents, site views, running room), its storage folder goes to the Trash, after confirmation inside the sidebar.
- D10 Runs are admitted by `RunRegistry`: at most one run per project, and at most one run in the app that uses a given site kind (one site account in two tabs at once invites bot checks); CLI and OpenRouter participants run in parallel across projects; the ledger row states both limits. A site participant's page is the site agent of that kind in the room's project, never the first agent of that kind in the app; a site kind with no agent in the room's project is disabled in Add participant with the reason.
- D11 The project map is bounded by path count as well as bytes: past the path cap the tree folds into directories with file counts; a project folder inside a larger repository lists `git ls-files -- .` relative to the folder.
- D12 Web participants of a project room get one attachment per turn holding the project map and the history; when a site adapter cannot attach the file, the same text is inlined and truncated to the composer limit and the turn goes on. An OpenRouter participant's budget comes from the model's `context_length` (GET /api/v1/models) at 3 characters per token, with `max_completion_tokens` (or 4096) reserved for the answer; history takes precedence, the map shrinks first.
- D13 A project room shows one line naming the sites and OpenRouter models its project map is sent to (D5 itself unchanged).
- D14 Agent's decisions: the node is labelled "No project" (the UI is English); a new project is a parent folder from the picker plus a name typed in the sidebar, so the test override of `pickFolder` covers both flows; `git` runs only through `execFile` from the main process, `git --version` is checked once per app run, and a missing `git` is a readable error with the map falling back to the directory walk (macOS without Command Line Tools opens a system install dialog on any `git` call).
- D15 Seams and studies come right before their consumer: each seam is a behaviour-neutral task (AC6), never bundled with a feature (owner's contract "No speculative abstractions"); each study covers what this plan builds — worktrees and write modes are studied by `docs/plans/roles.md`. The engine/policies split also belongs to roles.
- D16 Kind descriptors: `src/shared/kinds/` holds one descriptor per agent kind — label, logo, family (`cli | site | api`), static capabilities (`readsDisk`, `writesDisk`, `attachesFiles`, `hasModel`, `resumable`); capabilities that depend on the model (`tokenBudget` from `context_length`, the effort list from `supported_efforts`) come from `capabilitiesOf(kind, ModelSpec, catalog)`, never from the descriptor; `src/main/drivers/registry.ts` maps a kind to its driver factory. Kind branches (`isCliKind`, `isSiteKind`, `OPENROUTER_KIND`, `kind === '…'`: 22 files, room-view.ts 21, room-model.ts 12, agent-controller.ts 10, agents.ts 9, room.ts 7 — grep 2026-10-24) become capability checks or registry lookups; adding a kind is one descriptor and one driver.
- D17 One `ModelSpec { kind, model?, modelName?, effort?, web? }` in shared: `RoomParticipant` (room-model.ts:39) and `OpenRouterSettings` (openrouter.ts:52) are built on it; a role later is `ModelSpec` + name + count + instructions; stored shapes stay readable.
- D18 One file store in two layers: `src/main/store/atomic-file.ts` (text; temp `<file>.<pid>.tmp` + rename; writes serialised per path, the order room.ts keeps today with `enqueue`, room.ts:205-215; stale temp files of dead pids removed at start — three `agents.json.<pid>.tmp` lie in the owner's data folder today) and `src/main/store/json-file.ts` on top (size cap, version field, migration chain). Writers moved onto it: room history `.md` (room.ts:120), room records (room-archive.ts:21), OpenRouter conversations (conversation-store.ts:32), app state (state-file.ts:16). The capture tool's writers (capture-sites.ts:58, capture-auto.ts:195) stay as they are: no version, no second consumer.
- D19 Storage: app state version 2 is a new file `<userData>/state.json`; `agents.json` is never written by this branch, so a build from `main` keeps its own file and both builds run on one data folder without destroying each other's state; the first start without `state.json` migrates from `agents.json` (D3). Per project `<userData>/projects/<id>/{rooms/, chats/}`; name and realpath live only in the project index of `state.json`; no `project.json` until roles need one; role runs are rooms in mode `orchestrated`, so no `runs/`. `shared/rooms` and `shared/openrouter` of today stay as "No project" storage, untouched.
- D20 Project lifecycle: every main service that holds per-project state implements `closeProject(id)` and registers at start; `src/main/projects/service.ts` calls the registered list and imports no other service. `RunRegistry` (D10) lives in main beside the room service.
- D21 IPC by domain: `src/shared/ipc/{agents,rooms,projects,openrouter}.ts` under one registry with today's validation; `src/main/ipc/<domain>.ts` registers each; the renderer sees `AppApi` only. Sidebar tree as data: `src/shared/sidebar-tree.ts` reducer (project → section → item, collapse, selection) with rooms and agents as cases.
- D22 Turn profile and context pack: `TurnProfile { cwd, mode: 'plan' | 'write', isolation, web }` is the input of the CLI argv builder and of the driver factory, the single place that forbids `bypassPermissions` and `--dangerously-bypass-approvals-and-sandbox`. `src/main/runs/context-pack.ts` composes `{ text, files[] }` for a recipient from `ContextProvider[]` (history, project map; later branch diff, command output, single files), each with a priority and a budget share, against `capabilitiesOf` (D16); drivers only deliver it. Every pack is recorded by reference: the turn's entry holds a digest (range of history entry ids sent, the run nonce, hash of each provider's content, text size, file names and sizes), provider content other than history is stored once per hash in `<rooms>/<id>.packs/<hash>.md`, a pack is rebuilt from the record exactly, and `roomPaths` (room-archive.ts:103) includes the packs folder so a deleted room trashes it. Two declared fixes come with the cut (AC6 exceptions): one nonce per run in every rendering (today CLI and web prompts draw a fresh nonce per turn, room-history.ts:93-94, while `history.md` and OpenRouter use the run's), and a web attachment built from the turn's `seen` entries instead of the live room `.md` (room.ts:434), which today lets a broadcast web participant read same-round replies once the history passes 12 000 characters.

## Assumptions
- After the upgrade no agents exist, so a pre-upgrade room with a site participant under "No project" cannot continue until the owner adds that site's agent there.
- Project data lives in the app's data folder, never inside the project directory; the only file the app writes into a project is a saved plan.
- Room CLI sessions of a project are looked up by Claude under the project folder and therefore appear in the owner's `claude --resume` list for that project; that is accepted and the sessions carry the room title.
- A project is identified by the realpath of its folder; two projects on one folder are refused.
- If T03 finds no way to keep hooks out of a `-p` turn, D8 falls back to today's cwd (`<shared>/rooms/<kind>-<n>`) with `--add-dir <project>` for Claude and whole-disk read for Codex, recorded in the task's NOTES with the T03 evidence.
- While this plan runs, the working copy is on branch `projects`: `npm start` from it is the new build. A build of v0.0.1 elsewhere keeps working on the same data folder (D19).
